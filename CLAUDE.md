# [Project Name]

## Security (non-negotiable)
- Never put secrets, API keys, or tokens in client/frontend code. Secrets live only in environment variables.
- The client never talks to the database or third-party APIs directly. All access goes through a backend layer that validates input and enforces security.
- Validate and sanitize every input on the server. Never trust data coming from the client.
- Enforce authorization on every endpoint: a user can only access their own data. Changing an ID in a request must never expose another user's data.
- Enforce access control at the data layer too (row-level rules / scoped queries), so a bug in app code still can't leak other users' records.
- Use a vetted, managed solution for authentication. Never hand-roll login, sessions, or password hashing.
- Apply least privilege everywhere: database roles, API keys, and permissions get only what they actually need.

## Working style
- Before any non-trivial task: plan first and show me the plan before writing code.

- Write and run tests for important logic.

## Stack
- Frontend: Android (Kotlin), Jetpack Compose + Navigation-Compose, Material3. compileSdk 34, minSdk 26, JVM 17.
- Backend: none (device-local app). The "backend layer" is the camera itself, reached over BLE → SSH tunnel → PTP/IP.
- Database: none in Phase 1 (connection state is an in-memory `StateFlow`).
- Auth: SSH keyboard-interactive to the camera, using credentials read from BLE CC17. Full BouncyCastle is installed at startup (`BcFix`) because Android's stripped "BC" lacks EC.
- Hosting: n/a (sideloaded APK). Project root: `android/`.

## Key commands
- build: `cd android && ./gradlew :app:assembleDebug` (wrapper Gradle 8.11.1 + Android Studio JBR; AGP 8.9.2, compileSdk/targetSdk 36). On Windows use `gradlew.bat` from PowerShell — the sh script breaks on the space in the project path. Output: `app/build/outputs/apk/debug/app-debug.apk`.
- release: `:app:bundleRelease` → `app/build/outputs/bundle/release/app-release.aab`. R8 minify+shrink is ON (keep rules in `app/proguard-rules.pro`); signing reads `android/keystore.properties` (git-ignored, see `keystore.properties.example`), falls back to the debug key when absent.
- compile-check: `:app:compileDebugKotlin`
- test: `:app:testDebugUnitTest` (junit available; no tests yet in Phase 1).

## Authorization model
- Single-user device app talking to one camera the user physically controls; no multi-tenant server, so per-user data isolation doesn't apply. The relevant boundary is **secrets**: SSH password + fingerprint are masked by default and only revealed via in-memory Developer Mode (never persisted). Raw protocol logs are gated behind the same Developer Mode toggle.

- **Phase 12 — Human Perception Layer** (`liveview/perception/`) sits BETWEEN `SceneComparator` and `ReferenceStateMachine` (wired only in `ReferenceMonitorManager`): `HumanPerceptionEngine.evaluate()` replaces each signal's `matched` with a perceptual decision and attaches a `PerceptualSignal` (noticeability, importance, confidence, directionConfidence, trend, severity, dead zone, hysteresis state) — downstream (state machine → `ReferenceAlertRules` → future Copilot reasoning) consumes ONLY perceptual verdicts, never raw deltas. Key invariants:
  - **Evaluators are pure functions** (`PerceptualEvaluator` objects, zero mutable fields, zero literals); ALL state (amplitude hysteresis, rolling history, spike damping, trend) lives in the engine. Every tunable — dead zones, saturations, `CurveSpec` curves, exposure component weights, strategy weights, salience, enter/leave, history params — lives in `PerceptualThresholds` (STRICT/MEDIUM/LOOSE) / `PerceptualTuning` (runtime override via the Developer "Human Perception" panel, in-memory only, exposed through `MonitoringSession.setPerceptualTuning`).
  - **Two hysteresis layers compose serially, no double latch**: amplitude (enter ~0.20 / leave ~0.10 on noticeability, hold in the band) feeds the existing 5-frame temporal state machine unchanged. The history window keeps RAW samples; single-frame spikes are damped toward the rolling median (factor 0.15) so transients never latch but sustained changes catch up.
  - **Exposure is a strategy-weighted composite** (mean/median/p95/p99/coverage/32-bin histogram divergence/subject-region stats) with a subject-priority floor — a drifted subject is never averaged away under HUMAN/PRODUCT/VEHICLE. Subject-region stats come from `RegionLumaStats` walking the exposure scan's existing pixel buffer (region set via `AnalysisRegionRegistry` by the reference monitor; `SubjectExposureResult` slot in `VisionContext`). `ReferenceExposureProfile` gained optional `histogramSignature` + `subjectExposure` (legacy profiles → weights renormalize away).
  - Raw cosine never leaves `SimilarityEvaluator` (perceived-match buckets); drift messages get severity adverbs via `PerceptualMessages` (the engine rewrites `message`; alert-rule latch logic unchanged). Threshold values are first-pass estimates — hardware validation pending.
- **Phase 13 — Assistant Instruction Layer** (`liveview/instructions/`) is a pure TRANSLATION layer between the perceptual verdict and presentation — no new perception, no second alert system. `InstructionTranslator.annotate()` runs in `ReferenceMonitorManager` between `HumanPerceptionEngine.evaluate()` and `ReferenceStateMachine.update()` and fills ONLY the new `ReferenceSignalResult.instruction` slot; `message` keeps its perceptual meaning end-to-end (never rewritten). `ReferenceAlertRules` drift text = `instruction?.message ?: message`. - **Phase 14 — Voice Guidance System** (`liveview/voice/`) is an OUTPUT-ONLY consumer of the two existing guidance streams (Phase 13 selected instruction + AlertConfig-gated telemetry alerts) — never a decision source; visual alerts untouched. Pure-Kotlin scheduling core (injected `clock: () -> Long`, JVM-tested) behind the `VoiceSpeechEngine` seam; `voice/AndroidTtsSpeechEngine` is the ONLY file importing `android.speech.tts` (async init drops not-ready utterances; `stop()` never fires the finished callback — utterance-id guarded). Key invariants:
  - **`VoiceKey` is a stable semantic identity** (AssistantAction / AlertType wrappers + `ReferenceMatched`), NEVER derived from spoken text — all dedupe/cooldown/merge/obsolete-removal keys on it; `VoiceTemplates` phrases are presentation only. - **Phase 16.2 — Shot Identity Extraction** (`liveview/reference/creative/identity/`) makes the Creative Scene Model describe *what makes THIS shot unique* rather than classifying the scene — WITHOUT literal pixel matching and WITHOUT structurally touching reasoning/matching/storyboard/alerts/telemetry. Root cause fixed: the analyzer quantized continuous measurements into a few categorical buckets (two different portraits both → `Portrait/Close-up/Warm/Right Third`) and discarded the distinguishing info. New additive layer, derived ONCE at import from signals the app already produces:
  - **`ShotIdentity`/`ShotTrait`** (`identity/ShotIdentity.kt`): continuous, distinctiveness-scored traits (`ShotTraitDimension`: subject position/scale, edge anchoring, negative-space volume+direction, subject↔background separation, tonal key/contrast, grid balance/density, warmth/cast magnitude, isolation, semantic distinction). **`distinctiveness` = deviation of the measured value from a neutral anchor** (extreme = distinctive; middling drops below the floor). Anchors/saturations live in `ShotIdentityThresholds` (STRICT/MEDIUM/LOOSE, DEFAULT=MEDIUM; first-pass, hardware-pending). Pure `ShotIdentityExtractor` computes the deterministic traits from the existing `CreativeAnalysisContext`; `SemanticExpert` adds ONE `SEMANTIC_DISTINCTION` marker (top concept's cosine margin over the median).   - **Identity-shaped importance is ORDERING-ONLY.** `applyIdentityImportance` reshapes the categorical baseline so each `CreativeAspect`'s weight reflects HOW distinctive the shot is on that axis (`DIMENSION_ASPECTS` is the single ShotTraitDimension→CreativeAspect coupling; aspects with no trait keep the baseline; the aspect SET never changes).
